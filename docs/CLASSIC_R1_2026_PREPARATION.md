# classic r1 大会復帰と直交時間最短経路の準備

classic r1 は2025年度全日本大会時のROMのまま、2026年10月7日の数日前にも迷路を正常走行したとユーザが報告した。この実機の状態を復帰比較の基準とする。現在は機体と迷路が手元にないため、ソースの復元準備と時間最短経路のPC検証を先行する。

## ブランチと作業場所

| 用途 | ブランチ | 作業ツリー |
| --- | --- | --- |
| 大会基準版の再調整 | `feature/classic-r1/competition-2026` | `../nightfall-fw-classic-baseline` |
| 新しい経路導出の準備 | `feature/f405/orthogonal-time-planner` | `../nightfall-fw-classic-r1` |

再調整ブランチは `v1.0.0` / `stable/classic/unit001/s20260404-nationals` と同じ `b426b1f729ea9071c88a6de8cad7948a0dfe1a96` から作成した。両ブランチをoriginへ保存する。経路開発の取り込み先は再調整ブランチとし、F413の開発履歴を一括マージしない。元の `nightfall-fw` 作業ツリーのF413調整値、WORKLOG、書込みツールなどの未コミット変更は保持する。

経路開発ブランチも大会基準版を土台とする。`control.c`、`drive.c`、`run.c`、OPモード、探索、センサ、Flash処理、既存solver/path、全classic/mini調整値は基準版と同一。追加APIは候補経路を生成するだけで、通常の最短走行入口へ接続していない。

## 再現ビルド

再調整用作業ツリーで実行する。

```sh
cmake --preset Release
cmake --build --preset Release --target nightfall_classic_r1_0
```

2026年10月7日のビルドはGNU Arm GCC 15.2.1で成功。メタ情報は `b426b1f`、`DIRTY=0`、`Release`、`t1.0`。RAM 81,480 B、CCMRAM 60,024 B、Flash 169,504 B。

生成物は `build/Release/nightfall_classic_r1_0.{elf,bin,hex}`。今回のBINのSHA-256は `82f42732326c4a19919b040cdda0b460b9d654819e92eb657c5ee3423e37bd7d`。ビルド日時とブランチ名が埋め込まれるので、再ビルド時のハッシュ一致は要求しない。実機に残る大会ROMとのバイナリ一致はまだ比較していない。

## 機体の元に戻ってからの順序

1. 現在の大会ROMを消す前に、F405内蔵Flashのアプリと保存領域を読み出して保存し、読戻しとSHA-256でバックアップを確認する。特にsector9 `0x080A0000` は距離校正、sector10 `0x080C0000` はセンサ校正、sector11 `0x080E0000` は迷路。タグだけではこれらを再現できない。
2. 現行ROMの起動情報、機体個体、使用モードとcase、電源条件、ゴール設定を記録する。安定版の `runtime_settings.yaml` は `(1,0)` と書かれているが自動適用されず、タグのclassicコードのゴールは中央2×2 `(7,7)/(7,8)/(8,7)/(8,8)`。実機のゴールと照合する。
3. 保護領域を消さない書込み条件を確認して、再調整ブランチの旧経路版を適用する。全消去は行わない。F413用UARTコマンド表をF405へ流用しない。
4. 非駆動の起動・センサ確認から始め、ユーザが許可した浮上固定の駆動確認、低速床上確認、探索、従来最短の比較へ進む。最近の正常走行と同じ条件で差を切り分け、必要な調整だけを行う。
5. 正常走行したFW SHA、dirty状態、params、校正バックアップ、モードとcaseを新しいstableとして固定する。
6. その後に新プランナの候補を表示し、旧runnerの時間モデルとの整合と実機計算時間を確認してから最短入口へ接続する。旧経路方式を選べる状態で比較する。

今回はST-LINK、UART、書込み、モータ、ファン、走行、NVM読書きを一切実行していない。

## 軽量プランナの範囲

対応はclassicの16×16以下。動作候補は直進、小回り左右90度、大回り左右90度・180度で、斜めは生成しない。大回り許可は既存mode/case設定に従う。32×32を黙って切り詰めず、未対応として拒否する。mini r1の32×32対応には別のメモリ設計が必要。

Dijkstra法で、公称運動モデル上の最初のゴール進入時刻を最小化する。区画・4方位・直前の小90/大90/大180の3種類、開始専用1状態を区別し、16×16で最大3,073状態。旋回種類を残すのは、出口速度と半区画の距離の持ち分が異なるため。同じセルでも向きや境界速度の違いを潰さない。

時刻と親情報を各32bit、優先度付きキューとその位置を各16bitに固定し、探索用配列は36,876 B。動的確保は行わない。終了後のキューを経路の逆順復元に再利用し、成功時だけ出力へ反映する。前景スタックの1,536 Bキャッシュに接続区間の計算結果を保存し、同じ加減速計算の反復を減らす。

### 公称時間と走行処理の境界

採用した時間モデルはmini r2開発中に追加された `common/route/motion_time.*`。classicの180mm区画、43mm初期距離、既存の速度・加速度・旋回角加速度・入口出口距離・丸め係数で評価する。ケース1/2の角度補正値とcase3以降の角度積算時の理論角を区別する。APIのcaseは `run_shortest()` に渡す値で、OPの表示caseと常に同一ではない。例えば大会版mode2のOP case3は `run_shortest(2,4)` を呼ぶ。

**公称時間最短と、旧F405 runnerでの実時間最短は同一とは限らない。** 旧runnerは直線コードごとに速度を再計画し、初期区間、壁切れ前の等速区間、最後の半区画停止、センサ補正によって公称モデルと差が生じる。PCの比較一致は探索アルゴリズムの検証であり、その差を検証したという意味ではない。通常走行への切替前に、旧runnerの指令列との時間・速度・停止条件の照合が必要。校正された車体の壁余裕や新しい旋回連結も実機で確認する。

ゴール後の停止用に、その方向で壁までの既知直線を利用する。経路には必要な延長を含み、`goal_entry_us` と `stop_us`、`post_goal_cells` を分けて返す。走行側が付加する初期区間と最後の半区画は二重に経路へ入れない。大180の途中で最初のゴールを通り抜ける候補や、停止区間のない大回りゴール進入は除外する。

F405 map入力の未知壁と不一致壁は通行不可へ揃える。経路なし・無効入力・出力容量不足・時刻overflow時は出力を更新しない。設定を勝手に低速化したり、旧方式へ無言でfallbackしたりしない。

## 検証と再実行

詳しいコマンドと参照元は [PC検証README](../tools/f405_time_planner/README.md)。

| 検証 | 結果 |
| --- | --- |
| ASan/UBSan付き自己試験 | 6,137チェック、PC参照との242比較が一致 |
| 既存運動モデル回帰 | 1,195チェックPASS |
| 大会迷路2012〜2020の9件 × mode2〜7 × case1〜9 | 486条件中467経路、19条件は経路なし |
| 上記の理論角case3〜9 | PC参照との378比較が一致。19件の経路なしも参照と一致 |
| 独立した経路再生 | 壁通過、半区画の持ち分、初回ゴール、終端、斜めなしを検査 |
| 無効入力 | 未知壁、不一致、境界、NaN、時刻overflow、容量不足、重複領域、32×32拒否を検査 |
| 大会基準版のRelease | classicをクリーンな再調整ブランチでビルド成功 |
| プランナ既定OFF | mini/classic両Releaseビルド成功 |
| プランナ明示ON | classicの実ARMリンク成功。旧solver・全ログを残して容量確認 |

経路なし19件は全て16MM2015CXで、mode2 case3〜9、mode3/4/7 case6〜9。これは採用した速度・加速度・停止条件下での結果で、迷路自体が解けないという意味ではない。

ONビルドはRAM 120,408 B / 131,072 B、CCMRAM 60,024 B / 65,536 B、Flash 188,984 B。旧ログを削らず追加でき、RAM残り10,664 Bを確保した。これはlinkerの最小stack/heap予約を含む使用量。previewのビルド後チェックはさらに8 KiB以上の空きを要求し、Flashイメージがsector9へ届かないことも検査する。コンパイラの静的スタック出力はプランナ本体2,376 B、wrapper 272 B（別途呼出先と割込み分が必要）。実機での計算時間とスタック最大使用量は復帰後に測定する。
