# classic r1 大会復帰と直交時間最短経路の準備

classic r1 は2025年度全日本大会時のROMのまま、2026年10月7日の数日前にも迷路を正常走行したとユーザが報告した。この実機の状態を復帰比較の基準とする。10月7日は機体不在でソースの復元準備と時間最短経路のPC検証を先行し、10月10日に大会基準版の書込みと読戻し検証を完了した。その後、ユーザによる実走確認とファン調整を経て、下記の最短入口への適用に進んだ。

## 2026年10月10日: 新経路の実走成功・保存

適用後、ユーザから「上手くいきました」と報告を受けた。コード・調整値の追加変更はなく、`5cf9f7d` の構成を保存した。
保存タグは `stable/classic/unit001/s20261010-classic-r1-time-planner`。詳細と復元手順は [保存記録](../stable/classic/unit001/s20261010-classic-r1-time-planner/notes.md) を参照。
実走成功はユーザ報告で、mode/caseやコースの網羅確認、実機計算時間・スタック最大使用量の測定は含まない。

## 2026年10月10日: 実走確認後の最短入口への適用

ユーザが大会基準版で実走行に問題がないと報告し、探索の `fan_duty` のみ 100→80 / 150→110 に調整した。保存点は `664d880`。続く依頼により、用意済みの小回り＋大回り（斜めなし）の時間ベース経路導出を再調整ブランチへ適用する。

- 通常の `solver_build_path()` からclassic専用の経路導出へ接続。`run.c` / `drive.c` / 制御 / OP / 探索 / 全params / NVM処理は `664d880` のまま。
- `NIGHTFALL_CLASSIC_TIME_PLANNER=ON` を既定値とし、miniは従来solverを継続。OFFの比較ビルドも可能。
- 保存迷路の16bit配列を1セルずつ8bitへ変換。未知・矛盾壁は閉鎖し、生成済みパスへ従来の変換処理を重ねない。case8/9も斜めを生成しない。小回り限定caseの制約は維持。
- 角度積算フラグを実行時に渡す。準備版の「case1/2は全modeで補正角」という推定を修正（通常OPのmode3〜7はcase1/2も理論角）。
- 計算失敗・空経路は `path[]` と表示用配列を消去してfalseを返し、既存の走行前エラー停止へ進む。速度低下や旧solverへの自動fallbackは行わない。
- UARTの `[TimePath]` に公称ゴール時間・停止時間、計算時間、展開状態数、ゴール・停止延長と経路コードを出力する。
- worktree内でもコミット識別とdirty状態が古いまま残らないよう、ビルドメタ情報を各ビルド時に更新する。

### 検証範囲と残る差

ASan/UBSanで既存プランナ6,137チェック・242参照比較、共有運動モデル1,195チェック、歴史迷路9件×54条件（467経路、19経路なし、378参照比較）を再確認した。追加の本番呼出し列テストは `run_shortest()` → `solver_build_path()` → `run()` をそのまま実行し、HAL/駆動プリミティブだけを置換。258,045チェックで16bit迷路の変換、全54設定、壁切れ有無、理論角/補正角、前回成功後の失敗、無効mode、走行開始前の中止、斜め未呼出し、終端停止を確認した。これは閉ループ制御や実際の壁切れ位置のシミュレーションではない。

公称モデルは以前のままで、旧F405 runnerの距離ごとの逆算加速度、短直線での速度切替、壁切れ補正とは差が残る。**推定時間で選んだ経路であり、実走時間の最小性を保証しない。** 2015迷路の既知19条件は引き続き経路なしとして停止する。調整済みの走行動作を維持するため、今回これらの条件を緩和しない。

Releaseのclassic/miniおよび旧solver比較ビルド成功。時間版classicのRAMは104,888 B、CCMRAMは60,024 Bで、RAMの追加空き26,184 B。Flashは約186 KBで従来のsector0〜5書込み範囲内。静的スタックはプランナ2,376 B、adapter288 B、入口376 B（別途呼出先・割込みあり）。ポストリンクでRAM余裕と校正sector9境界を検査する。

今回の適用では実機書込み・モータ・ファン・NVM操作は行っていない。新経路の実機計算時間・スタック最大使用量・壁余裕・実走行は未確認。今後の変更も `../nightfall-fw-classic-baseline` で従来どおりビルド・USB-UART書込みできる。コマンドは [README](../tools/f405_time_planner/README.md) を参照。

## 機体の元に戻ってからの順序

1. 現在の大会ROMを消す前に、F405内蔵Flashのアプリと保存領域を読み出して保存し、読戻しとSHA-256でバックアップを確認する。特にsector9 `0x080A0000` は距離校正、sector10 `0x080C0000` はセンサ校正、sector11 `0x080E0000` は迷路。タグだけではこれらを再現できない。
2. 現行ROMの起動情報、機体個体、使用モードとcase、電源条件、ゴール設定を記録する。安定版の `runtime_settings.yaml` は `(1,0)` と書かれているが自動適用されず、タグのclassicコードのゴールは中央2×2 `(7,7)/(7,8)/(8,7)/(8,8)`。実機のゴールと照合する。
3. 保護領域を消さない書込み条件を確認して、再調整ブランチの旧経路版を適用する。全消去は行わない。F413用UARTコマンド表をF405へ流用しない。
4. 非駆動の起動・センサ確認から始め、ユーザが許可した浮上固定の駆動確認、低速床上確認、探索、従来最短の比較へ進む。最近の正常走行と同じ条件で差を切り分け、必要な調整だけを行う。
5. 正常走行したFW SHA、dirty状態、params、校正バックアップ、モードとcaseを新しいstableとして固定する。
6. その後に新プランナの候補を表示し、旧runnerの時間モデルとの整合と実機計算時間を確認してから最短入口へ接続する。旧経路方式を選べる状態で比較する。

10月7日の準備段階では実機操作を行っていない。10月10日は上記のROM保存・アプリ書込み・保存領域の読戻しまで完了した。次は手順4の起動・センサ確認と走行比較から再開する。

## 軽量プランナの範囲

対応はclassicの16×16以下。動作候補は直進、小回り左右90度、大回り左右90度・180度で、斜めは生成しない。大回り許可は既存mode/case設定に従う。32×32を黙って切り詰めず、未対応として拒否する。mini r1の32×32対応には別のメモリ設計が必要。

Dijkstra法で、公称運動モデル上の最初のゴール進入時刻を最小化する。区画・4方位・直前の小90/大90/大180の3種類、開始専用1状態を区別し、16×16で最大3,073状態。旋回種類を残すのは、出口速度と半区画の距離の持ち分が異なるため。同じセルでも向きや境界速度の違いを潰さない。

時刻と親情報を各32bit、優先度付きキューとその位置を各16bitに固定し、探索用配列は36,876 B。動的確保は行わない。終了後のキューを経路の逆順復元に再利用し、成功時だけ出力へ反映する。前景スタックの1,536 Bキャッシュに接続区間の計算結果を保存し、同じ加減速計算の反復を減らす。

### 公称時間と走行処理の境界

採用した時間モデルはmini r2開発中に追加された `common/route/motion_time.*`。classicの180mm区画、43mm初期距離、既存の速度・加速度・旋回角加速度・入口出口距離・丸め係数で評価する。ケース1/2の角度補正値とcase3以降の角度積算時の理論角を区別する。APIのcaseは `run_shortest()` に渡す値で、OPの表示caseと常に同一ではない。例えば大会版mode2のOP case3は `run_shortest(2,4)` を呼ぶ。

**公称時間最短と、旧F405 runnerでの実時間最短は同一とは限らない。** 旧runnerは直線コードごとに速度を再計画し、初期区間、壁切れ前の等速区間、最後の半区画停止、センサ補正によって公称モデルと差が生じる。PCの比較一致は探索アルゴリズムの検証であり、その差を検証したという意味ではない。通常走行への切替前に、旧runnerの指令列との時間・速度・停止条件の照合が必要。校正された車体の壁余裕や新しい旋回連結も実機で確認する。

ゴール後の停止用に、その方向で壁までの既知直線を利用する。経路には必要な延長を含み、`goal_entry_us` と `stop_us`、`post_goal_cells` を分けて返す。走行側が付加する初期区間と最後の半区画は二重に経路へ入れない。大180の途中で最初のゴールを通り抜ける候補や、停止区間のない大回りゴール進入は除外する。

F405 map入力の未知壁と不一致壁は通行不可へ揃える。経路なし・無効入力・出力容量不足・時刻overflow時は出力を更新しない。設定を勝手に低速化したり、旧方式へ無言でfallbackしたりしない。

### 経路なし19条件の追加診断（2026-10-07）

19件の直接原因は全て発進区間。2015迷路は `(0,0)` から北へ1区画進むと北が壁で、東への右折が必要になる。現モデルでは大回りの発進接続を使えず、小回り入口までの加速距離は初期43 mm + 半区画90 mm = 133 mmとなる。

| 設定（run_shortestのcase） | 小回り速度 mm/s | 低速域加速度 mm/s² | 停止から必要な加速距離 mm |
| --- | ---: | ---: | ---: |
| mode2 case3〜9 | 700 | 1,000 | 245.0 |
| mode3 case6〜9 | 1,200 | 4,000 | 180.0 |
| mode4 case6〜9 | 1,400 | 7,111.11 | 137.8 |
| mode7 case6〜9 | 2,000 | 11,111.11 | 180.0 |

この速度範囲は低速域なので、必要距離は `v²/(2a)`。全て133 mmを超える。PC追試では全19条件の到達状態数が開始状態の1個だけで、小回り限定にしても経路なしだった。診断用コピーで最初の接続直線だけ加速度上限を必要値の1.001倍へ緩和し、他の経路制約・調整値を維持すると全19条件が成立した。この緩和は原因切分け専用で、本実装へは適用していない。

大会版 `run.c` は半区画直線の壁切れバッファで `driveC_wallend(..., v_next)` を呼び、`drive.c` は `velocity_interrupt = spd` として目標速度を直接切り替える。一般の `driveA()` も渡された距離と入口・出口速度から加速度を逆算する。したがって、paramsの直線加速度を全区間の絶対上限とみなす現モデルとは一致しない。参照プランナも同じモデルを共有するため、参照との一致だけではこの差を検出できない。

優先対策は、既存runnerの発進・短直線・壁切れ前後の指令をPC上で再現し、F405用の成立判定と時間評価を合わせること。段差状の速度指令に実機が追従する時間は実機復帰後に確認する。低速設定への変更や加速度引上げを、今回の結果だけを根拠に自動適用しない。一般には旋回間の速度差・ゴール後停止距離・未知壁でも経路なしになるが、今回の19件はそれ以前の発進で停止している。

ONビルドはRAM 120,408 B / 131,072 B、CCMRAM 60,024 B / 65,536 B、Flash 188,984 B。旧ログを削らず追加でき、RAM残り10,664 Bを確保した。これはlinkerの最小stack/heap予約を含む使用量。previewのビルド後チェックはさらに8 KiB以上の空きを要求し、Flashイメージがsector9へ届かないことも検査する。コンパイラの静的スタック出力はプランナ本体2,376 B、wrapper 272 B（別途呼出先と割込み分が必要）。実機での計算時間とスタック最大使用量は復帰後に測定する。
