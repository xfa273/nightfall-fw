# mini_r3 探索ログ回収・不安定動作の解析（2026-10-10）

## 結論

V2互換ST-LINKのまま、MCU側USART1とMac側を一時的に115200bpsへ揃え、FRAMに残る6301件をチェックサム一致で回収した。CSVは10走行分に分割済み。回収以前にリングから上書きされた記録は含まない。

ユーザー確認により、実際の開始位置は左下(0,0)、北向き。一方、回収したFWと直近探索ログはSTART=(11,10)、北向きだった。これが今回の早期停止と早すぎるゴール認識を説明する。さらに、case1のゴール後再発進には前壁を無視して前進する独立した実装上の問題がある。位置合わせゲインを先に変更する根拠はない。

本作業は回収と原因確認。FW、調整値、開始・ゴール座標は変更していない。機体のリセット・書き込み・走行も実施していない。UARTのみ揮発設定115200bpsを残した。

## case2: 座標のオフセットにより迷路内部を外周として扱う

run006/007/009は同じ経路で、内部座標(14,15)、東向き、action28で `full_unreachable`。終端は `completed=1 route_failed=0 abort=none`。制御タイムアウトやCPU停止ではなく、FWが未探索区画への経路なしとしてセッションを終了している。

実開始(0,0)に対してFW開始(11,10)なので、北向きが一致し区画移動が正常だった範囲では、実位置は内部座標から(11,10)を引いたものになる。

| 地点・方向 | 内部座標 | 推定実座標 | FWで除外される通路 |
| --- | --- | --- | --- |
| 東側へ開いている地点 | (15,10) | (4,0) | x=16への移動 |
| 北側へ開いている地点 | (12,15) | (1,5) | y=16への移動 |
| 最後の停止地点、東向き | (14,15) | (3,5) | 左=北、y=16への移動 |

最後の左センサはrun006/007/009で19/26/27、壁情報 `0xCC`、セル `0x66`。左=北の壁を検出していない。それでも `f413_search_step_make_smap()` は `cy != MAZE_SIZE - 1` を必要とするため、その先を探索しない。ユーザーも「停止地点は16×16迷路の内部」「通れる未探索区画が残っていた」と確認。最後の左通路自体は記憶なし。

保存迷路の接続性を調べると、停止地点から到達できるのは26区画。run009で訪れた26区画と一致し、未訪問セルを起点にしたFW同等のBFSでも停止地点はstep=-1となった。これは**誤った座標原点と16×16境界を前提にした内部地図**の結果であり、実迷路の探索完了を意味しない。

対策は実配置に合わせて `params/mini_r3_0/params.h` の `START_X/START_Y` を0/0へ戻すこと。迷路サイズを増やしたり境界チェックを外して回避する問題ではない。座標を修正した後は、現在FRAMの地図も旧原点で記録されている点に注意する。今回その地図の削除・書き換えは行っていない。ゴール座標は実迷路で意図するものを保持・確認する必要がある。

## case1: 誤ったゴール認識に続く、前壁を無視した再発進

case1はGOAL→FULLの二段階。現在のGOAL3=(12,10)は、今回の実開始位置との不一致により実位置(1,0)に相当する。run004/008/010はここに西向きで到達してゴール扱いとなる。

最新run010のイベント:

| seq | 動作 | 記録 |
| --- | --- | --- |
| 13 | GOAL到達 | 内部(12,10)、西向き |
| 14 | 45mm減速停止 | 1672ms |
| 15 | 10mm後退 | 264ms。直前の停止位置で読んだFR/FL=3145/2784を保持 |
| 16 | 再発進の決定 | `next=forward`、`smap=-1`、前壁を消した `wall=0x55` |
| 17 | 55mm前進 | 598ms、目標331mm/sに対し実測142mm/s、角度約6°ずれ |
| 19 | FULL到達不能 | 内部(11,10) |
| 21–22 | 保存ガード・終了 | `map_save_guard`、`completed=0 route_failed=1` |

FR/FL=3145/2784は停止直後・後退前の壁読みで、後退後の瞬時値ではない。45mmの前壁LUT基準は約2508/2494で、停止時に近い前壁があることを示す。位置合わせ失敗を直接記録したイベントではない。

原因箇所は `platform/stm32f413/HM_Nightfall_f413_preorder/Core/Src/f413_search_step.c`:

1. `f413_search_step_run_phase_restart_entry()` が停止後に `read_and_write_current_wall(true)` を呼ぶ。
2. `true` は相対前壁ビット `0x88` を強制的に消す、初回発進用の扱い。
3. 10mm後退後、次フェーズの経路選択をせず、forward決定を記録する。
4. `run_entry_section()` が10+45=55mm前進し、座標を1区画進める。

同じ症状が3本で反復しており、ユーザーの壁突入という観察と整合する。開始座標を直すと今回の場所での誤ったゴール認識は解消するが、**前壁のある正しいゴールでもこの再発進処理は危険な動作を選び得る**。

修正方針は、フェーズ境界で座標・向き・前壁情報を保ち、次フェーズの経路を決めてから、停止位置に対応する旋回・進入動作を選ぶこと。初回発進の「前は空いている」前提を再利用しない。case3/5/7もこの共通関数を通るので対象になる。

## 前壁位置合わせの記録

case2の(12,10)での180°切り返しは3本とも完了。FM1/FM2の位置誤差はそれぞれ0.80/0.00mm、1.05/0.70mm、0.80/0.30mm。run009のFM1のみrelaxed、それ以外はcompleteで、abortはない。少なくとも今回回収した直近の異常は、前壁位置合わせゲインの再調整より座標設定と再発進処理を先に扱うべきである。

## V2接続復旧と現在のUART状態

SWDはCube CLI、st-util、OpenOCD等で接続失敗が続いた。V3への交換は行わず、対象SNを絞ったUSBプローブリセット等の後、Cube CLI HOTPLUG、要求1000kHz（実950kHz）で短いUSART書き込みが成功した。これはSWD不安定の根本原因を特定したことを意味しない。

成功した揮発レジスタ操作:

```text
-c port=SWD freq=1000 mode=HOTPLUG sn=066BFF545771485067014053
-nv
-w32 0x4001100C 0x000C
-w32 0x40011008 0x0364
-w32 0x4001100C 0x200C
-r32 0x40011008 8
```

USART1 BRR/CR1読み戻し `00000364 0000200C`。100MHz PCLK2で約115200bps。途中の失敗した書き込みでCR1だけ変わった状態もあったが、この成功シーケンスとUART応答で復旧を確認した。アプリやNVMの書き込みではない。

その後のUARTコマンドは `|`（状態・calibration読み取り）、`>`（保存ログdump）、`@`（保存迷路dump）、`|`（再確認）。モータ・ファン・走行コマンドは実行していない。ST-LINK FW更新やアプリflashもしていない。

**現在は機体側も115200bps。リセット・電源再投入でFW既定の921600bpsに戻る。** リセットしていない現在の状態なら、次の読み取りコマンドで再回収できる。満杯のFRAMは約104秒かかるので既定30秒では足りない。

```sh
python3 tools/logging/trace_bin_dump.py --port /dev/cu.usbmodem1102 --baud 115200 --timeout 120
```

115200bpsで状態取得と全ログdumpに成功したことまでは確認済み。V2互換機一般の速度上限や、SWD側不調の原因は断定しない。
