# 改善探索の MCU 評価と F413 組み込み準備

2026-09-06、`codex/f413-exploration-ready`。比較 UI の最短経路情報優先探索を、
動的メモリ確保のない共通 C コードへ移し、F413 の実 CPU で評価した。
本ブランチの固定 mini_r2 プロファイル向けアダプタは実装済み、既定は **OFF**。
接続機のアプリケーション Flash・FRAM・identity は変更していない。
モータ、ファン、探索走行は実行していない。

## 実装した構成

- `common/route/mcu_slalom_time_planner.c`: 整数マイクロ秒の最短時間グラフ。
  旋回ガードを証明付きの事前計算テーブルへ置換し、姿勢ごとの成立判定を再利用する。
  計算状態を保持し、1 work unit ごとに中断できる。経路の幾何条件と停止尾部まで
  必要な開放辺を復元し終わるまで、厳密解として返さない。
- `common/exploration/exploration_policy.c`: 初回ゴールまでは足立法。その後は
  楽観的最短時間経路に必要な未知辺を優先して観測する。全必要辺が既知開放なら
  この有限グラフ・時間モデルでの最適性を確定する。
- `f413_exploration.c`: 次セルへの到着を予測して計算し、既存の保護された走行待ち
  ループで継続する。到着時は姿勢・観測世代・最初の辺を再検査する。
  未完了・不成立・古い結果では足立法へ戻す。加速終了時の直進・減速義務も守る。
  走行境界で経路計算を同期的に完了まで回すことはしない。
- 計算待ちと完了の切り替えで往復する実例を検出したため、足立法へ戻った後は
  新しい実観測が増えるまで足立法を維持する。厳密な完了証明はその間も受け入れる。
  安価な直交 BFS を使う暫定探索も比較可能だが、有限予算で悪化する場合があったため
  `pending_surrogate=false` を既定とする。

探索用の近似移動コストと、最短走行の厳密な目的関数は別である。
探索先選択を近似しても完了判定を近似しない。詳細な契約は
[共通ポリシー](../common/exploration/README.md)、
[MCU 経路計算器](../tools/solver_host/MCU_SLALOM_ORACLE.md) を参照。

## 非駆動の実機計測

STM32F413 Rev A、100 MHz、ST-LINK `066CFF545771485067013914`。
`-O2` の独立計測プログラムを SRAM にだけロードし、DWT のサイクル数を測定した。
32MM2023HX の探索リプレイから得た 5 段階の部分地図について、未知を開放とする
楽観投影と、未知を閉鎖とする保守投影をそれぞれ計算した。

| 部分地図 | 楽観投影の CPU 時間 | 保守投影の CPU 時間 |
|---|---:|---:|
| 初期観測 | 1.252 秒 | 0.0067 秒 |
| ゴール初到達 | 11.118 秒 | 0.199 秒 |
| 探索中盤 | 5.613 秒 | 0.212 秒 |
| 最短経路確定時 | 2.178 秒 | 0.654 秒 |
| 全壁既知・評価専用 | 1.115 秒 | 1.115 秒 |

最も重かったゴール初到達の楽観投影は、最適化前の 52.216 秒から **4.70 倍**高速化。
それでも長いので一括実行は不適切である。最適化後の `step(1)` の最大実測値は
20.94 μs、32×32 の初期化は 0.829 ms。16×16 の 5 部分地図では、楽観投影の
全計算が 0.093〜0.455 秒、最大 `step(1)` は 20.21 μs だった。
いずれも標本中の最大値であり、WCET の保証ではない。

F413 上の経路ワークスペースは 32×32 で 202,456 bytes、16×16 で 51,368 bytes。
ポリシーはホスト計測で 30,384 bytes（最大 32×32）。本ブランチのアダプタは
自動トレースの既存 212,992 bytes を排他的に借用する。借用中は自動記録の開始を
拒否し、終了時に解放する。探索イベント記録は別領域を使う。トレースの永続形式は
変更しない。MCU 共通モジュールは 32×32 に対応するが、本ブランチの実機ビルドの
`MAZE_SIZE` は 16 のままである。

実アダプタの 13 ケースも SRAM 上で通過した。16×16 の到着時検査は最大
0.937 ms、予測ジョブ開始は 0.085 ms、計算 poll は最大 0.843 ms だった。
加速中の完了延期、矛盾した壁での中止、ゴール到達を再進入前に記録すること、
同じ地図での計算待ち時の足立法維持と、厳密証明の受け入れを検査した。
実際のトレース貸出コードについても 8 条件を確認し、借用中には NVM format の
カウンタ代用関数すら呼ばれないことを確認した。

| 本ブランチの Debug F413 ビルド | 静的 RAM・予約領域 | Flash |
|---|---:|---:|
| 既定 OFF | 240,592 bytes | 182,804 bytes |
| ON | 272,848 bytes | 249,672 bytes |

OFF のバイナリに新しいポリシー・計算器のシンボルがないことも確認した。
F405 の既定ビルド、既存探索ホスト試験も通過している。

この SRAM 計測では通常の制御・センサ IRQ を止めている。Flash からの命令取得、
割り込み競合、スタック高水位、1 kHz 制御周期のジッタ、実走行の壁読み位置や
停止遅延は未検証である。実装の poll 目標は 500 μs だが、実際には最後の 1 単位や
初期化コールバックの分だけ超過し得る。これを走行許可の判定に流用しない。

全計測の前後で Flash 全 1.5 MiB の SHA256 は一致した:
`5812cf7a75e31a4db82396b95ca9d115803a091dcab2f52ffaec78042b2b6ae1`。
実行後は元のアプリケーションへソフトウェアリセットしている。
計測の入口とコマンドは [SRAM ベンチマーク](../tools/hil/exploration_bench/README.md)。

## 計算量を制限した走行比較

同じ C コードをホストで実行し、次セルへ走る時間内に使える work unit 数を制限した。
以下は policy 64 単位/ms、oracle 20 単位/ms、暫定探索 OFF の条件。
mini_r2 mode1 case1 の走行速度、固定 F413 mode2 case8 の最短目的関数を使う。
所要時間は探索終了までの**移動モデルの推定値**で、スタートへの帰還を含まない。
CPU の計算待ちは有限予算・フォールバックとして反映するが、実機走行時間ではない。

| ハーフ決勝迷路 | 従来 GOAL→FULL | C 改善探索 | 短縮 |
|---|---:|---:|---:|
| 2019 | 517.181 秒 | 468.633 秒 | 9.4% |
| 2022 | 434.250 秒 | 275.499 秒 | 36.6% |
| 2023 | 454.880 秒 | 407.452 秒 | 10.4% |

oracle 20/50 単位/ms × 暫定探索 ON/OFF × 3 迷路の全 12 条件で終了し、
完了時の楽観・保守・真の迷路の最短時間が独立した再計算でも一致した。
ただし常に従来より速いわけではない。2019 の 50 単位/ms・暫定 OFF は
517.242 秒、2023 の 20 単位/ms・暫定 ON は 466.338 秒で、従来より遅い。
計算予算を増やすほど探索時間が単調に減るわけでもない。

実測平均では oracle 20 単位/ms は約 14%、policy 64 単位/ms は約 14% の CPU に
相当する例がある。単位ごとのコストは一定ではなく、初期化・到着時検査・IRQ 等も
別に必要なので、これは比較シナリオの目安である。実機で確保できる予算の証明ではない。
全条件、再現コマンド、失敗を検出した旧条件の記録は
[MCU_READINESS](../tools/exploration_sim/MCU_READINESS.md) にまとめた。

## 有効化と新機体ブランチへの移植

本ブランチの固定プロファイルをビルドする場合:

```sh
cmake --preset Debug -B build/exploration-enabled \
  -DNIGHTFALL_F413_EXPLORATION_ENABLED=ON
cmake --build build/exploration-enabled --target nightfall_stm32f413
```

通常の preset は OFF のまま。ON のときも対象は mode1 case1 の GOAL→FULL 探索だけ。
GOAL の実到達をフェーズの停止・後退・再進入より前に記録し、探索終了後の停止や
帰還は既存の走行処理を使う。テーブルの入力指紋をビルド時に再検査するため、
プロファイルや経路モデルを変更したまま古い数値でビルドできない。

新機体対応の通常チェックアウト `3910fa6` は、本ブランチと出発距離、加速度、
最高速度、旋回形状、経路グラフが異なる。`route_precomputed_compatible()` は
その最新ブランチ内の互換性であり、本計算器との互換性を意味しない。
そのため現時点で `NIGHTFALL_F413_RUNTIME_CONFIG` の実機には改善判定を適用せず、
足立法を維持する。古い最短性証明を mini_r3 等へ流用しない。

新機体側へ移すときは、新しい経路モデルの十分な依存辺を含む下界と、実行可能な
経路の上界が一致することを確認する必要がある。通常経路が存在しない場合だけ
追加される recovery 経路もあるので、単なる速度定数の差し替えでは済まない。
通常経路だけを証明対象とし、その既知経路が実行可能であることを保証する方法も
考えられる。新しいモデルに対応するまでは失敗時に足立法へ戻す。

最新側には排他的な `try_borrow_idle_scratch` API、ゴール後の再進入動作、NVM 保護が
既にある。古い `f413_search_step.c` や `f413_trace_log.c` を上書きせず、それらを
保ったまま方向選択・到着予測・poll・完了通知の接続点を移す。
新機体モデルの一致と、制御 IRQ を動かした固定機体での時間計測を済ませてから、
別途許可された床上の走行試験で壁読み・加速・停止・帰還を確認する。

最新 `3910fa6` に対する接続部分は、別ブランチ
[`codex/f413-exploration-runtime-scaffold`](https://github.com/xfa273/nightfall-fw/tree/codex/f413-exploration-runtime-scaffold)
の `6e8db0d` に保存した。既存の探索・新機体・NVM 保護を保った 5 ファイルの変更で、
OFF/ON ともビルド済み。ただし ON でも明示的に足立法を維持する**接続枠のみ**であり、
新機体で改善アルゴリズムが動作したという結果ではない。RAM は両方 274,120 bytes、
Flash は OFF 367,140 / ON 367,564 bytes。通常チェックアウトには変更を加えていない。
詳細な差分と残るモデル条件は、そのブランチの `docs/EXPLORATION_RUNTIME_SCAFFOLD.md`。

条件付き primary 下界と、既知 nominal 経路の上界を組み合わせる移植案については、
[最新モデルの監査](EXPLORATION_RUNTIME_MODEL_AUDIT.md) に整理した。局所 7,872 条件では
小回りによる時間の逆転はなかったが、最新実行グラフへの移植・上界検証はまだ実装していない。

計算予算を制限した C の探索順は、保存済みの UI リプレイでも確認できる:

```sh
tools/exploration_sim/run.sh --port 8877 \
  --replay build/exploration_sim/mcu-policy-half2023-ui.json
```

元の計算結果から UI 用 JSON を再生成する手順は `MCU_READINESS.md` を参照。
C 実装であることと計算予算を画面に表示し、観測・位置・時刻を元のリプレイから保持する。
